# Техническое задание: Удалённый SSH-доступ к GPU-подам Kubeflow через WebSocket

## 1. Контекст и проблема

В нашей корпоративной среде доступ к GPU-ресурсам предоставляется исключительно через Kubeflow – браузерный JupyterLab или code-server. Среда жёстко изолирована:

- На машинах нет интернета, только внутренняя сеть.
- Аутентификация происходит через корпоративный SSO с сессионной кукой (authservice_session).
- Istio Proxy пропускает HTTP-трафик только на один фиксированный путь, соответствующий запущенному «блокноту» (например, `/notebook/namespace/user/my-server/`). Любые дополнительные сегменты пути блокируются.
- Никакого SSH, scp или прямого доступа к подам.
- Перенос файлов возможен лишь через UI блокнота, что крайне неудобно для автоматизации.
- Попытки использовать chrome-mcp-server (управление через DOM) ненадёжны, а подходы с Kubeflow Pipelines или монтируемыми виртуальными окружениями убивают скорость исследовательского цикла из-за необходимости пересборки образов при каждом изменении зависимостей.

Цель: дать разработчику и AI-агенту привычный SSH-интерфейс (ssh, scp, rsync, sshfs) к вычислительному окружению на GPU, работающий через существующий HTTPS-канал, с сохранением корпоративной аутентификации и без изменения инфраструктуры Istio.

## 2. Общая архитектура решения

Решение состоит из двух частей:

- **Серверная** (внутри пода Kubeflow): минимальный HTTP/WebSocket-прокси, который пробрасывает трафик к локально запущенному SSH-серверу.
- **Клиентская** (на локальной машине): прокси-команда для стандартного SSH-клиента, преобразующая TCP-поток в WebSocket-соединение.

После настройки разработчик может выполнять `ssh my-gpu-server` или `scp file my-gpu-server:/workspace/`, и всё будет прозрачно работать через HTTPS с корпоративной кукой.

## 3. Детальное описание серверной части

### 3.1 Что должно быть в Docker-образе

Образ должен содержать:

- OpenSSH-сервер.
- Python (желательно 3.10+) и библиотеку `websockets` (или аналогичную) для реализации прокси.
- SSH-сервер конфигурируется для прослушивания только loopback-интерфейса (127.0.0.1:22) и принимает подключения без пароля (пустой пароль разрешён). Это безопасно, так как перед проксированием уже проверена корпоративная кука.
- Пользователь для входа — `jovyan` (как в остальных образцах Kubeflow), домашняя директория `/home/jovyan`, куда монтируется Persistent Volume для сохранения данных.
- При старте контейнера генерируются SSH-ключи хоста (если не были сохранены) и запускаются sshd и наш прокси-сервер.

### 3.2 Прокси-сервер

Прокси-сервер слушает порт 8888 и обслуживает единственный путь, заданный для блокнота. Никакой проверки куки не производится, так как предполагается, что Istio пропускает только уже аутентифицированные запросы.

Логика работы:

- При получении HTTP-запроса **без** заголовка `Upgrade: websocket` сервер может возвращать 200 OK (для проверок готовности) или 404.
- При получении запроса с заголовком `Upgrade: websocket` (и опциональным `?ssh=true` в query) сервер:
  - Выполняет WebSocket handshake.
  - Немедленно открывает TCP-соединение к `127.0.0.1:22`.
  - Запускает двунаправленный проброс данных между WebSocket и сокетом SSH.
  - При закрытии любой из сторон аккуратно завершает соединение.

Реализация может быть выполнена на `websockets` (asyncio) или `aiohttp`. Поддержка нескольких одновременных WebSocket-сессий — nice to have, а не жёсткое требование (для разных клиентов или параллельных команд scp/rsync). Аутентификация полностью делегирована вышестоящему прокси (Istio), поэтому дополнительная валидация не требуется.

---

Таким образом, серверная часть становится ещё проще, а безопасность остаётся на прежнем уровне за счёт инфраструктуры. Весь фокус — только на качественном проксировании трафика.

### 3.3 Сборка и публикация образа

Сборка образа происходит на машине с доступом к внутреннему репозиторию пакетов (PyPI, apt-зеркало). Необходимо обеспечить офлайн-установку всех зависимостей внутри образа.

Примерная структура Dockerfile:

- Базовый образ: Kubeflow `base` (ubuntu-based с пользователем `jovyan`), как в остальных образцах репозитория.
- Установка openssh-server, генерация ключей (или скрипт при старте).
- Копирование Python-скрипта прокси.
- Установка pip-зависимости (websockets) – желательно из внутреннего PyPI.
- Запуск: команда старта должна запускать sshd и затем Python-скрипт прокси.
- Пользователь контейнера непривилегированный (не root).

После сборки образ публикуется во внутренний Docker Registry.

### 3.4 Настройка в Kubeflow

В интерфейсе Kubeflow создаётся новый Custom Notebook Server:

- Указывается собранный образ.
- Порт 8888.
- При монтировании Persistent Volume (для рабочей директории `/home/jovyan`) нужно убедиться, что права пользователя `jovyan` позволяют писать в неё.
- Запустить сервер и запомнить полный URL (например, `https://kubeflow.corp.com/notebook/team-ns/user123/my-ssh/`).

## 4. Клиентская часть

### 4.1 Прокси-скрипт для SSH (kube-ssh-proxy)

На локальной машине создаётся Python-скрипт (или отдельное приложение), который:

- Принимает два аргумента: хост и порт (как это делает ProxyCommand, но реально они не используются, т.к. целевой URL фиксирован).
- Читает URL блокнота из переменной окружения `KUBEFLOW_NOTEBOOK_URL`.
- Читает сессионную куку из переменной `KUBEFLOW_SESSION_COOKIE` (или из файла `~/.kubeflow_cookie`).
- Устанавливает WebSocket-соединение к `wss://<хост из URL>/<путь>?ssh=true` (URL собирается из KUBEFLOW_NOTEBOOK_URL, протокол меняется на wss).
- В заголовки WebSocket-запроса добавляет Cookie с `authservice_session=...`.
- После успешного соединения скрипт должен передавать данные из stdin в WebSocket (в бинарном режиме) и из WebSocket в stdout. Таким образом SSH-клиент будет думать, что общается с обычным TCP-сокетом.

Для корректной работы необходимы:

- Обработка сигналов завершения.
- Keep-alive (если WebSocket-соединение обрывается, скрипт должен завершиться, чтобы SSH мог переподключиться).

### 4.2 Конфигурация SSH

В файле `~/.ssh/config` добавляется запись:

```
Host my-kube-gpu
    HostName kubeflow.corp.com
    User jovyan
    ProxyCommand /usr/local/bin/kube-ssh-proxy %h %p
    StrictHostKeyChecking no
    UserKnownHostsFile /dev/null
```

При этом `HostName` и `User` фактически не важны (аутентификация и адрес определяются URL и кукой), но ssh требует их наличия.

После этого можно выполнять:

```bash
ssh my-kube-gpu
 scp local_file my-kube-gpu:/workspace/
 rsync -avz ./ my-kube-gpu:/workspace/
```

### 4.3 Управление кукой

Чтобы не копировать куку каждый раз вручную, можно написать небольшой вспомогательный скрипт, который:

- Получает свежую куку, автоматизируя вход (например, через headless браузер раз в сутки) – но это опционально.
- Сохраняет её в файл `~/.kubeflow_cookie` с ограниченными правами доступа.
- Прокси-скрипт перед соединением читает куку из этого файла, если переменная окружения не задана.

## 5. Требования к реализации и ограничения

- Серверная часть должна быть асинхронной. Поддержка нескольких параллельных SSH-сессий — nice to have.
- Не использовать пути с дополнительными сегментами, кроме заданного для блокнота. Все опции передавать через query string.
- Кука `authservice_session` **не проверяется** сервером — аутентификация полностью делегирована Istio.
- При реализации прокси-скрипта убедиться, что он корректно работает с бинарными данными (SSH-трафик не текстовый).
- Образ должен собираться в условиях отсутствия выхода в интернет – все зависимости должны быть доступны через внутренние зеркала или предварительно загружены.
- Для первой версии пользователь жёстко задан — `jovyan`. Возможность смены пользователя через параметр в query string — в будущем.
- Клиентский прокси-скрипт использует библиотеку `websockets` (asyncio) — ту же, что и серверная часть. Запуск через `uv run` — никаких ограничений на зависимости нет.

## 6. Тестирование и приёмка

- После развёртывания сервера и настройки SSH-конфига команда `ssh my-kube-gpu` должна открывать shell на удалённой машине (поде).
- Установка пакетов внутри сессии (через внутренний PyPI) должна работать без ограничений.
- Должна быть возможность выхода и повторного входа без потери состояния (PV сохраняется).
- scp и rsync должны передавать файлы корректно и без искажений.
- При обрыве сетевого соединения SSH должен переподключаться без необходимости вручную обновлять куку (кука живёт долго, но если истекает – можно настроить автоматическое обновление).

## 7. Заключение

Данное решение даёт разработчику полноценный удалённый терминал в изолированную среду Kubeflow, не нарушая корпоративные политики безопасности. Это фундамент для комфортной ручной работы и надёжная основа для автоматизации через AI-агента, который сможет выполнять любые shell-команды и передавать файлы стандартными средствами.
